# PR: 歌詞の自動タイミング（音声＋歌詞 → 行ごとの LRC）

`feat: automatic line timing from the song and the written lyrics (v0.11)`

## 何を追加したか

「曲とタイミング」に **自動で時間を合わせる** を追加しました。曲をブラウザの中で聴き取り、
**書かれた歌詞**の各行の開始時刻を求めて、行ごとの手動タイムとして入れます
（`timing.lineTimes` ＝ タップ同期や数値入力と同じ場所）。以降は既存の編集
（タップ・入力・ドラッグ・LRC 書き出し）がそのまま使えます。

```
曲を読み込む → 歌詞を貼る → 自動で時間を合わせる → 気になる行だけ直す → LRC を書き出す
```

- **音声は送信しません。** 認識も解析も端末の中で完結します（初回だけ認識モデルを取得）。
- 日本語・英語・簡体字/繁体字に対応。
- 自信を持てなかった行は赤く表示し、手で直すと印が消えます。

## 実装の要点

**認識結果ではなく歌詞を合わせます。** 欲しいのは文字起こしではなく時刻だからです。
認識器は歌い方を聞き違え、行を落とし、間奏で空耳を作り、中国語では繁体字で返します。
そこで**認識結果の語は信じず、時刻だけ**を使い、書かれた歌詞のトークン列と曲全体で
単調な編集距離（Needleman–Wunsch）で対応づけます。各行は本当に一致した語から時刻を取ります。

- `src/09b_autolrc.js` — 対応づけ本体（DOM も音声も触らない純粋な計算。だから外で試せます）
- `src/09a_han.js` — 簡体字 ↔ 繁体字の対応表（OpenCC の語彙から生成）
- `src/10b_whisper.js` — ブラウザ内認識（Transformers.js、`*_timestamped` のみ、版を固定）
- `src/10c_features.js` — 音の特徴。**時刻の後始末にだけ**使います
- `src/12_ui.js` / `app/*` — ボタン・進行表示・要確認の印・7言語ぶんの文言

初期案からの変更点と、その理由は `docs/AUTO_TIMING.md` に書きました。要約:

1. **帯付き DP をやめました。** 認識器が一節落とすと 100 トークン以上ずれ、帯がその経路を切ります。
2. **2行だけの表でのたどりをやめました。** 古いセルを読んで静かに壊れます。Hirschberg にしました。
3. **「ほぼ無料で読み飛ばせる」境界をやめました。** 歌詞の最初の3分の1を捨てる経路が見つかりました。
4. **音だけでの時刻推定はやめました。** 実測で VAD は 64 行に対し 35 区間、オンセットはモーラ数の 4.6 倍。
   後始末にだけ使います。
5. **認識の窓を 30 秒・移動 15 秒にしました。** 窓が前奏の上で開くと認識器は歌を1行も返しません
   （実曲で、22 秒の前奏のあとの窓が「都」1文字だけを返しました）。半分ずつ動かして、
   どの瞬間も2つの窓に入るようにしています。中国語の中央値が 4.57 秒 → 0.75 秒になりました
   （代わりに時間は2倍。実測は `docs/AUTO_TIMING.md`）。
6. **GPU で時刻を出せないモデルは、隠さず CPU で走らせます。** Base と Small の fp16 は
   WebGPU で壊れます（Base は1語だけ、Small は**語は正しいのに全部の時刻が同じ**）。
   隠すと、精度を理由に選んだモデルが黙って Tiny にすり替わってしまうので、CPU に回します。
7. **既定のモデルを Tiny から Base に変えました。** 実曲で Tiny は当てになりません
   （中国語で中央値 3.25 秒、日本語では前奏明けの8行が 20 秒以上ずれる）。GPU のある端末では
   Base は CPU で動くので待ち時間は延びますが、**間違った時刻を速く出すより、正しい時刻を
   少し待って出すほうがいい**と判断しました。Tiny は「速い・軽い」選択肢として残し、
   メニューにそう書いています（遅い端末や、ダウンロードを小さくしたいとき）。

## 検証

### オフライン（`cd dev && npm test`、22 + 4 件）

実曲の回帰テストを入れました。**実際の4分の曲の語ごと認識結果と、手で作った LRC** の2つだけを
入力にして、同じ行頭時刻を出せるかを測ります（`dev/fixtures/i_wont_turn_back.*`）。

| | 結果 |
|---|---|
| 行数 | 64 |
| 中央値誤差 | **0 ms** |
| p90 誤差 | **0 ms** |
| 300ms 以内 | **96.9%** |
| 最大誤差 | 1143 ms（"Your name, your name" — 同名の繰り返しが3箇所あり、2番目を選んだ） |
| 一致した行 | 62/64 |

ほかに、聞き違え・落ちた行・空耳（幻聴）・繰り返しのサビ・間奏・前奏・分割された語・
かな/カタカナ/濁点・簡体字↔繁体字・ユーザーが書いた時刻タグ・区間だけの認識結果・
逆行するタイムスタンプ・音の特徴による補正を、それぞれ個別のテストにしています。

### 実ブラウザ（`python dev/autolrc_browser_test.py --model tiny`）

日本語・英語・中国語の音源（Windows の音声合成で作り、行頭時刻を正確に記録したもの。前奏4.2秒、
途中に5秒の間奏、低いベッド音つき）で、**実際にブラウザの中で認識させて**端から端まで測りました。

| 言語 | モデル | 端末 | 所要 | 中央値 | p90 | 300ms以内 |
|---|---|---|---|---|---|---|
| 英語 | Tiny | WebGPU | 3.6s | **0.25s** | 1.98s | 83% (5/6) |
| 日本語 | Tiny | WebGPU | 25.8s | **0.34s** | 1.18s | 50% (3/6) |
| 中国語 | Tiny | WebGPU | 3.4s | **1.23s** | 5.03s | 17% (1/6) |

- 日本語は3行目・6行目が 0.1 秒以内、全行 1.2 秒以内。誤差は行の語の聞き違えによるものです。
- 英語は5行が 0.3 秒以内。1行だけ 2.4 秒ずれました（認識器が行の先頭語を落とした行）。
- 中国語は苦手で、Whisper Tiny が歌詞の一部を別の語として返し（「縫」→「奉」、「間」→「聞」）、
  3行目までと4行目以降の対応がずれます。**一致度の低い行として印が出る**ので、
  利用者はその行だけ直せます（これが印を付けた理由です）。

### 実曲（`python dev/autolrc_realsong.py`）

合成音はきれいすぎて実力が出ないので、**実際に配信されている曲**で測りました。音源と歌詞は
著作物なのでリポジトリには入れず（`.gitignore` の `dev/samples/`）、入口と手順だけを残しています。
正解は人が合わせた同期歌詞（lrclib.net）で、**先に音と突き合わせて確かめてから**使いました。

| 曲 | モデル | 端末 | 所要 | 中央値 | p90 | 最大 | 300ms以内 | 1秒以内 | 一致した行 |
|---|---|---|---|---|---|---|---|---|---|
| Lemon (ja, 4:34) | Tiny | WebGPU | 58s | 0.38s | 21.50s | 27.22s | 41% | 62% | 36/37 |
| Lemon (ja, 4:34) | **Base** | **CPU** | 97s | **0.42s** | **1.29s** | 5.11s | 43% | **84%** | **37/37** |
| Lemon (ja, 4:34) | Small | CPU | 245s | 0.38s | 1.18s | 11.73s | 46% | 84% | 37/37 |
| 孤勇者 (zh, 4:15) | Tiny | WebGPU | 25s | 3.25s | 44.13s | 59.27s | 12% | 42% | 27/40 |
| 孤勇者 (zh, 4:15) | **Base** | **CPU** | 94s | **0.75s** | **2.92s** | 13.73s | 30% | **60%** | **40/40** |
| 孤勇者 (zh, 4:15) | Small | CPU | 210s | 1.82s | 3.22s | 13.63s | 18% | 40% | 37/40 |

- **Tiny は実曲では足りません。** Lemon の最初の8行は前奏に負けて 20 秒以上ずれます。
  CPU の Base にすると Lemon は p90 1.29 秒、中国語でも中央値 0.75 秒です。実曲では Base を勧めます。
- **既定は Base にしました。** 実曲では Tiny が当てになりません（下の実測。中国語で中央値 3.25 秒、
  日本語では前奏明けの8行が 20 秒以上ずれる）。GPU のある端末では Base は CPU で動くので
  待ち時間は延びますが、**間違った時刻を速く出すより、正しい時刻を少し待って出すほうがいい**
  と判断しました。Tiny は「速い・軽い」選択肢として残し、メニューにそう書いています
  （遅い端末や、ダウンロードを小さくしたいとき）。
- 認識の窓を半分ずつ動かすぶん、**処理時間は2倍**になります。それでもこの交換は割に合うと
  考えました: 4分の曲で Base が約1分半、その代わり中国語の中央値が 4.57 秒 → 0.75 秒、
  40行すべてが一致します。自動で LRC を作るのに1分少々待つのは許容範囲だと判断しています。
- 中国語の正解は繁体字なので、入力を簡体字に変換して入れています（利用者が簡体字で打つのと同じ状況）。
- 中国語は Base でも 300ms 以内は 30% です。誤った行には印が出るので、そこを直す前提です。
  Lemon を Small で合わせたときは**印が1行も出ませんでした**。
- Small はダウンロードも時間も2倍以上で、Lemon ではわずかに良く、中国語では Base より悪い
  という結果でした。**大きいほうが常に良いわけではありません。**
- Base / Small の **WebGPU は使えません**（上記）。CPU で走らせると決めたうえで選んでいます。
- 既知の誤り: 同じ語の繰り返し（Lemon の最初の8行のような前奏明け、`"Your name, your name"`）は
  隣の繰り返しを選ぶことがあります。

## 既知の制約

- 認識モデルの取得に一度だけダウンロードが必要です（Tiny 41MB〜）。ネットワークが細い環境では
  時間がかかります。オフラインでも従来どおりタップ同期・数値入力で作れます。
- CPU 実行は GPU よりかなり遅くなります（実曲4分で Base 97 秒、Small 4 分）。
- **中国語は Tiny では精度が足りません**（実曲で中央値 3.25 秒）。Base を選ぶか、手で直す前提です。
- 同じ語の繰り返しが多い行（"Your name, your name" など）は、まれに隣の繰り返しを選びます。
- 行の先頭の語を認識器が落とすと、その行は少し（〜1秒）後ろにずれます。一致度の印が出ます。

## 使い方

1. 曲を読み込む（mp3 など）
2. 歌詞を貼る（`[間奏 8]` も使えます）
3. **自動で時間を合わせる** → 確認 → 実行（初回はモデルをダウンロード）
4. 赤い行だけ再生して確かめ、タップ／数値入力／ドラッグで直す
5. **LRC を書き出す**
