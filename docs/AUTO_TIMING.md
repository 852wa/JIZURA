# 自動タイミング（歌詞のない曲でも、歌詞だけで時刻を合わせる）

音声と、すでにある歌詞から、**各行の開始時刻を自動で求めて LRC を作る**ための実装です。
`dev/autolrc_test.js`（22件）と `dev/autolrc_features_test.js`（4件）がオフラインで検証し、
`dev/autolrc_browser_test.py` が実ブラウザで端から端まで確かめます。

## なぜ「認識結果」ではなく「歌詞」を合わせるのか

やりたいのは文字起こしではなく**時刻合わせ**です。ところが認識器は歌詞をそのまま返しません。

- 歌い方を聞き違える（`never` → `neva`、`君` → `気`）
- 行まるごと落とす、同じ節を二度出す
- 前奏・間奏で勝手な言葉を作る
- 長い単語を分割して返す（`never` → `ne` + `ver`）
- 中国語では**繁体字**で返すことがある（利用者が簡体字で打っていても）

そこで、認識結果の**言葉は信じず、時刻だけ**を使います。書かれた歌詞のトークン列と、
認識器の返したトークン列を、曲全体で**単調な編集距離（Needleman–Wunsch）**で対応づけ、
各行は「本当に一致した語」の時刻から決めます。

```
歌詞（書かれたとおり）  ──┐
                          ├─ トークン列にして全体を対応づけ ─→ 行ごとの開始時刻
認識結果（語ごとの時刻）──┘
```

一致しなかった行は、**前後の行の間に落ちた認識語**（聞き違えた行）か、
**前後の行のあいだを文字数で按分**（歌われなかった行）で置きます。
`[間奏 8]` と書いた行は書いた長さを保ちます。

## 構成

| ファイル | 役割 |
|---|---|
| `src/09b_autolrc.js` | 歌詞 × 認識結果の対応づけ。DOM も音声も触らない純粋な計算 |
| `src/09a_han.js` | 簡体字 ↔ 繁体字の対応表（OpenCC の語彙から生成。`dev/build_han_table.py`） |
| `src/10b_whisper.js` | ブラウザ内認識（Transformers.js / ONNX Runtime Web）。語ごとの時刻を返す |
| `src/10c_features.js` | 音の特徴（歌っている区間・アタック）。時刻の後始末にだけ使う |
| `src/12_ui.js` | 「自動で時間を合わせる」ボタンと進行表示、要確認の印 |
| `app/body.html` / `app/style.css` / `app/english.py` / `app/i18n_*.py` | 画面と7言語ぶんの文言 |

結果は `timing.lineTimes`（手で合わせた時刻と同じ場所）に入ります。以降は既存の
タップ同期・数値入力・ドラッグ・LRC 書き出しがそのまま使えます。

## 実装で分かった、そのままにできない点

**1. 帯（バンド）で DP を絞ってはいけない。**
最初は対角線の周りだけ計算する帯付き DP にしていました。曲全体ではほぼ対角ですが、
認識器が一節を落とすと 100 トークン以上ずれます（実測 149）。帯はまさにその経路を切ってしまい、
64 行のうち 18 行しか当たりませんでした。いまは帯なしの全体 DP です。

**2. ロールバックする2行だけの表でたどってはいけない。**
メモリを惜しんで2行だけ持ち、たどりながら復元する実装は、**古いセルを読んで**
静かに壊れます（30 秒に一度、必ずと言っていいほど）。いまは Hirschberg の分割統治で、
2行ぶんのメモリのまま正しく復元します。

**3. 「ほぼ無料で読み飛ばせる」境界を作ってはいけない。**
前奏の雑音に耐えるため、最初と最後の数語をほぼ無料で読み飛ばせるようにしたところ、
**歌詞の最初の3分の1を捨てる**経路が見つかってしまいました。読み飛ばしはどこでも同じコストです。

**4. 行の開始は「最初に一致した語」でよい。**
一致した語すべてから開始時刻を推定して中央値を取る案は、実曲の計測で**悪化**しました
（p90 が 0ms → 270ms）。行の途中の語時刻は揺れるので、最初の一致語のほうが正確です。

**5. 音だけでは歌詞の時刻は求まらない。**
これは実装前の計測で確認しました（`docs/` の調査メモ）。実曲で、
声域エネルギーの VAD は 64 行に対して 35 個の「区間」しか出せず、行頭までの距離の中央値は 2.5 秒。
オンセットは毎秒 10.1 個で、歌詞のモーラ数（毎秒 2.19）の 4.6 倍あり、累積で辿ると 8 秒以上ずれます。
音の特徴は**時刻の後始末**（間奏に落ちた行を押し出す、アタックに寄せる）にだけ使っています。

**6. 認識結果の先頭に紛れ込む1語を落とす。**
前奏のある音源では、認識器が 0.00 秒に1語だけ余計な語を出します（3言語すべてで再現）。
それが歌詞の1行目の語と同じだと、1行目が 0 秒になり以降すべてが押し出されます。
「2番目の語との間隔が、それ以外の語間隔より極端に広い」という**時間だけの基準**で落としています
（音量の基準は素材によって効いたり効かなかったりで、汎用になりませんでした）。

**7. 認識の窓は 30 秒だが、15 秒ずつ動かす。**
窓が**前奏の上で開くと、認識器は歌を1行も返しません**。実曲で測ると、22 秒の前奏のあとに
歌が始まる曲で、0〜30 秒の窓は「都」1文字（20秒ぶんの長さの幻聴）を返して終わりでした。
同じ区間でも、窓をずらして歌が窓の内側に入るようにすると正しく取れます。
そこで窓を半分ずつ動かし、**どの瞬間も2つの窓に入る**ようにしています。同じ箇所を2回
聞き取った結果は両方そのまま渡します。フレーズが二度出てくるぶんのコストは編集距離の
「挿入1」ですが、**まったく聞き取れなかった行は時刻そのものを失う**ので、そちらのほうが高くつきます。

実測（実曲2曲、`dev/autolrc_realsong.py`、窓 30 秒・移動だけ変えた比較）:

| 曲 | モデル | 端末 | 移動 30s | 移動 15s |
|---|---|---|---|---|
| Lemon (ja) | Tiny | WebGPU | 0.66s / p90 16.2s | **0.38s** / p90 21.5s |
| Lemon (ja) | Base | CPU | 0.42s / p90 1.29s | 0.42s / p90 1.29s |
| Lemon (ja) | Small | CPU | 0.38s / p90 1.18s | 0.38s / p90 1.18s |
| 孤勇者 (zh) | Tiny | WebGPU | 7.37s / p90 41.6s | **3.25s** / p90 44.1s |
| 孤勇者 (zh) | Base | CPU | 4.57s / p90 20.2s | **0.75s** / p90 **2.92s** |
| 孤勇者 (zh) | Small | CPU | **1.46s** / p90 14.6s | 1.82s / p90 **3.22s** |

どの組み合わせでも良くなるわけではありません（Small の中国語は中央値が少し悪くなります）が、
**勧める組み合わせ（Base・CPU）でいちばん効きます**: 中国語の中央値が 4.57 秒 → 0.75 秒、
40行すべてが一致するようになります。代わりに**かかる時間は2倍**です（Lemon で 53 秒 → 97 秒）。
止められる進行表示があるので、精度を取るほうを既定にしました。

## 認識モデルと精度

| モデル | ダウンロード | 用途（画面にも出ます） |
|---|---|---|
| Tiny | 41MB（CPU）/ 77MB（WebGPU） | 速い・軽い。**遅い端末や、ダウンロードを小さくしたいとき**の選択肢 |
| Base | 77MB（CPU のみ） | **既定。おすすめ。** WebGPU では word 時刻が壊れるため CPU で動かします（画面には `(CPU)` と出ます） |
| Small | 241MB（CPU のみ） | 高精度。同上。いちばん大きい（大きいほど良いとは限らないのは下の実測のとおり） |

**既定は Base です。** 実曲で Tiny は当てになりませんでした（下の実測）。GPU のある端末では
Base は CPU で動くので待ち時間は延びますが、**間違った時刻を速く出すより、正しい時刻を
少し待って出すほうがいい**という判断です。速さを優先したいときは Tiny を選べます。

- `*_timestamped` の ONNX 書き出しだけを使います（素のモデルの word 時刻は向こうの issue 追跡で
  何度も壊れており、リポジトリ自身が timestamped 版を勧めています）。Transformers.js は
  バージョン固定です（word 時刻の品質が版で変わった前例があるため）。
- WebGPU では fp16、CPU では q8 を読みます。**WebGPU + q8 は意味の通る文だが中身が違う出力**
  （"Ой Monet我說 couch notrekil…"）を返し、q4 はさらに悪く、whisper-base では36秒の曲に対して
  `"I"` 一語しか返しませんでした（`dev/autolrc_probe.py` で再確認できます）。
- **WebGPU の fp16 は Base と Small では使えません。** Base は36秒の曲に `"I"` 一語、
  Small は**語は正しいのに全部の時刻が `[29.98, 29.98]`** になります（後者のほうが厄介です。
  文だけ見ると正しいので）。CPU では同じモデルが正しく動くので、**GPU で使えないモデルは
  隠すのではなく CPU で走らせます**。隠すと、選んだ理由（精度）が黙って別のモデルに
  すり替わってしまうためです。

## 検証

```
cd dev && npm test                       # オフライン（実曲の回帰 + 音の特徴）
python dev/page_check.py                 # 7つのビルドを読み込んでエラーがないか
python dev/serve_autolrc.py 8791 <曲のフォルダ> &     # テスト用の音源とモデルのミラー
python dev/autolrc_browser_test.py --model tiny       # 合成音（行頭時刻が既知）
python dev/autolrc_realsong.py --dir <曲のフォルダ> --prefix <URL 以下の名前> --model base --device wasm
```

`dev/autolrc_test.js` には**実曲の回帰**が入っています。実際の4分の曲の語ごと認識結果と、
手で作った LRC、その2つだけを入力にして、LRC と同じ行頭時刻を出せるかを測ります
（`dev/fixtures/`）。

### 実曲での端から端までの測定

合成音（音声合成）はきれいすぎて実力が出ません。**実際に配信されている曲**で測るための
入口が `dev/autolrc_realsong.py` です。曲のフォルダに

```
mysong.mp3          音源
mysong.txt          書かれた歌詞（1行1行）
mysong.truth.json   {"lines": [{"start": 12.34, "text": "..."}]}
mysong.ref.lrc      元にした同期歌詞（出典を残すため）
```

を置いて、`dev/serve_autolrc.py` の第2引数にそのフォルダを渡してから実行します。
**音源と歌詞は著作物なのでリポジトリには入れません**（`.gitignore` の `dev/samples/`）。
正解の時刻には、人が合わせた同期歌詞（lrclib.net のもの）を使い、**先に音と突き合わせて
確かめてから**使います（前奏のあとの最初の歌声と1行目が一致するか、`?mode=probe` で見えます）。

測った2曲（2026-10、Windows / Chrome、WebGPU あり）:

| 曲 | モデル | 端末 | 所要 | 中央値 | p90 | 最大 | 300ms以内 | 1秒以内 | 一致した行 |
|---|---|---|---|---|---|---|---|---|---|
| Lemon (ja, 4:34) | Tiny | WebGPU | 58s | 0.38s | 21.50s | 27.22s | 41% | 62% | 36/37 |
| Lemon (ja, 4:34) | **Base** | **CPU** | 97s | **0.42s** | **1.29s** | 5.11s | 43% | **84%** | **37/37** |
| Lemon (ja, 4:34) | Small | CPU | 245s | 0.38s | 1.18s | 11.73s | 46% | 84% | 37/37 |
| 孤勇者 (zh, 4:15) | Tiny | WebGPU | 25s | 3.25s | 44.13s | 59.27s | 12% | 42% | 27/40 |
| 孤勇者 (zh, 4:15) | **Base** | **CPU** | 94s | **0.75s** | **2.92s** | 13.73s | 30% | **60%** | **40/40** |
| 孤勇者 (zh, 4:15) | Small | CPU | 210s | 1.82s | 3.22s | 13.63s | 18% | 40% | 37/40 |

- 正解は lrclib.net の同期歌詞（Lemon は id 8948466、孤勇者は id 34493546）。
- 孤勇者の歌詞は**正解が繁体字**なので、入力を簡体字に変換してから入れています
  （利用者が簡体字で打つのと同じ状況。`09a_han.js` の対応表がここで効きます）。
- **Tiny は実曲では足りません。** Lemon の最初の8行は前奏に負けて 20 秒以上ずれ、
  孤勇者は中央値 3.25 秒でした。CPU の Base にすると Lemon は p90 1.29 秒、
  孤勇者でも中央値 0.75 秒になります。**だから既定は Base です**（Tiny は速い・軽いぶんの
  選択肢として残しています）。
  Small はダウンロードも時間も2倍以上かかり、Lemon ではわずかに良く、中国語では Base より悪い
  という結果でした（大きいほうが常に良いわけではありません）。
- 中国語はいちばん難しく、Base でも 300ms 以内に入るのは 30% です。一致度の低い行の印が出るので、
  そこを再生して直す前提です。Lemon を Small で合わせたときは**印が1行も出ませんでした**
  （`stats.low` が空）。

詳しい数値は PR の説明にまとめてあります。
